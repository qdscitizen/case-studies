一、问题是什么(客户视角)

Mick 登录 WordPress 后台,页面顶部出现一条「吓人」的数据库报错;同时更新任何插件都会失败,提示同样的错误。他已尝试:禁用四个待更新插件(无效)、发邮件给主机商(等回复中)。

二、报错原文(证据保留)

Update failed: WordPress database error: [The SELECT would examine more than MAX_JOIN_SIZE rows; check your WHERE and use SET SQL_BIG_SELECTS=1 or SET MAX_JOIN_SIZE=# if the SELECT is okay] SELECT wp_posts.ID FROM wp_posts INNER JOIN wp_postmeta ON ( wp_posts.ID = wp_postmeta.post_id ) INNER JOIN wp_postmeta AS mt1 ON ( wp_posts.ID = mt1.post_id ) WHERE 1=1 AND ( ( wp_postmeta.meta_key = '_alg_wc_pvbur_visible' AND wp_postmeta.meta_value != '' ) OR ( mt1.meta_key = '_alg_wc_pvbur_invisible' AND mt1.meta_value != '' ) ) AND wp_posts.post_type = 'product' AND ((wp_posts.post_status = 'publish')) GROUP BY wp_posts.ID ORDER BY wp_posts.post_date DESC LIMIT 0, 1

三、原因 —— 三层因果链

3.1 先纠正常见误解

误解真相
「用户选择的数量超过上限」无关。用户什么都没多选,只是更新插件这个常规动作
「WordPress 配置的上限」无关。MAX_JOIN_SIZE 是 MySQL 服务器(主机商)设的,WP 核心不管这个
「查询太复杂,WP 有 bug」WP 没坏。是某个插件生成了这条重查询,撞上了主机的防护栏

3.2 三层因果链(从表到里)

表层 · 主机设了防护栏
共享主机商为了防止一个租户的慢查询拖死整台服务器,把 MySQL 的 MAX_JOIN_SIZE 设得很低(如几万行)。含义:单条 SELECT 查询最多允许「扫描/检查」这么多行,超了直接拒绝执行。 相当于浏览器「脚本执行超时」的数据库版。
中层 · 这条查询扫描量天然爆炸
wp_postmeta 是 WP 里最大的表之一(每个产品几十条 meta,万产品站 = 几十万行)。 这条查询把 postmeta JOIN 了两次(别名 mt1),再按自定义字段 OR 过滤 —— MySQL 需要检查的行数是乘积级的,轻松超过几万行的上限。
里层 · 谁生成了这条查询?—— 指纹破案
看 WHERE 条件里的两个 meta_key:_alg_wc_pvbur_visible / _alg_wc_pvbur_invisible

meta_key 是插件的数据指纹(每个插件给自定义字段加独特前缀)。拆解前缀:
_alg = 作者代号(Algolplus)· _wc = WooCommerce · _pvbur = Private Visibility(隐藏产品的功能)

Google 精确搜索 "_alg_wc_pvbur_visible" → 命中 Algolplus 出品的 Private Products / 目录可见性类付费插件。 经查 WP.org 插件 API:该插件不在免费目录 —— 这解释了 Mick 为什么没想到它 (付费插件不显示在「待更新列表」里,他禁用的四个里自然没有它)。

3.3 为什么 Mick 禁插件无效(关键推理)

Mick 禁用的是四个「待更新的插件」(其中含报错 JSON 里正在更新的 woo-extra-product-options)。 但生成慢查询的是 另一个付费插件 —— 不在更新列表里,所以他禁错了对象,真凶还活着, 每次进后台/更新都照跑。

教训:禁用测试要覆盖「所有活跃插件」,尤其是「不显示在更新列表里的付费插件」—— 它们最容易被排除出嫌疑。

四、解决办法(已回复给 Mick 的三层方案)

层动作效果谁执行
① 快速验证(5分钟) 插件列表里找 Private Products / catalog visibility 类插件(Algolplus 出品)→ 停用 → 刷新后台/再试更新 报错消失 = 确认真凶 Mick 自己
② 根治 确认后:该插件更新到新版(反馈 Algolplus,这条双 JOIN 查询本身写得差);或不再需要「隐藏产品」功能就直接删除插件(残留 meta 无害) 问题不再发生 Mick
③ 治标(主机侧) 主机调大 MAX_JOIN_SIZE 或对该库 SET sql_big_selects=1。Mick 已联系主机 —— 把报错原文发给主机,他们知道改什么 错误立刻消失,但坏查询还在跑(只是允许跑了) 主机商
三层思维(修站通用框架):快速验证(确认真凶)→ 根治(消灭原因)→ 治标(绕过限制)。 顺序不要反 —— 只做③会让坏查询继续在后台跑,只是没人报警了。

五、知识点沉淀(可复用)

5.1 「从报错反推真凶」的指纹法 ⭐ 本案例核心

报错类型指纹在哪反查到什么
SQL 报错meta_key / 表名前缀生成该查询的插件
PHP Fatal Error文件路径 /plugins/xxx/src/File.php路径直接点名插件
JS 报错source URL / 组件名主题或插件的脚本
CSS 互殴类名前缀(.alg- .yith-)主题/插件
前端口径:就像报错 Cannot read properties of undefined at UserCard.vue:87 —— 文件名就是凶手的门牌号。SQL 里的 meta_key 就是数据库世界的文件名。
习惯:报错原文永远读完,里面的每个名字都值得 Google 一次(精确短语搜索)。

5.2 MAX_JOIN_SIZE / SQL_BIG_SELECTS 速查

项内容
归属MySQL 服务器变量(不是 WordPress 的)
作用限制单条 SELECT 允许扫描的最大行数,防慢查询拖死共享服务器
谁设置主机商(my.cnf / 面板);个人无法在 WP 里改
解法让主机调大,或对库执行 SET sql_big_selects=1(治标);优化/移除生成重查询的插件(治本)
英文沟通"The failing query joins wp_postmeta twice and exceeds your MAX_JOIN_SIZE limit. Could you raise the limit (or set sql_big_selects=1) for my database?"

5.3 meta_key 前缀速查(指纹库,持续积累)

前缀归属

六、已交付的回复(存档)

I'd zoom in on this part of the query: wp_postmeta.meta_key = '_alg_wc_pvbur_visible' / mt1.meta_key = '_alg_wc_pvbur_invisible' Those meta keys are added by a private products / catalog visibility plugin (the _alg_wc_pvbur_ prefix belongs to an Algolplus plugin). Since it's a premium plugin, it wouldn't appear in your "updates available" list — which may be why it wasn't caught when you disabled the four pending-update ones. Two things to try: 1. Find the culprit: check your plugin list for anything named like "Private Products" / "Private Store" / catalog visibility (by Algolplus). Deactivate it and reload the dashboard — the error should be gone. If it is, check that plugin for an update, or remove it if you don't need the "hide products" feature. 2. The host side: you did the right thing emailing your provider. MAX_JOIN_SIZE is a MySQL server limit (a protection on shared hosting), not a WordPress setting. They can raise it (SET SQL_BIG_SELECTS=1 or increase MAX_JOIN_SIZE) — send them the error and they'll know exactly what to change. Step 1 tells you whether the plugin is the trigger; step 2 removes the hard ceiling either way. Please report back what you find!
